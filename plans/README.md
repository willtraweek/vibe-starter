## How to run these plans

1. Commit `plans/` on its own (a docs-only PR is fine). Until 001 merges, `bootstrap` doesn't
   delete `plans/`, so don't create new projects from the template in between.
2. Do one PR per plan, in order, each branched from the latest `master` after the previous one
   merges. The drift checks assume exactly that. After 001 merges, every later PR gets the
   template's CI.
3. For each plan, either run `/improve execute plans/00N-….md` (a separate agent implements it
   in an isolated worktree, then its diff is reviewed against the plan) or hand the plan file to
   an agent in a fresh Conductor workspace. Update the plan's status row in the same PR.
4. Ship each PR with gstack `/ship`. Until 005 merges, two prompts need specific answers:
   - "Reorganize TODOS.md?" → **Leave as-is**.
   - "What runtime / does this project need tests?" → **doesn't need tests** (the template's CI
     runs the self-test).

   Expect `/ship` to bump the root `VERSION` and write `CHANGELOG.md`; 005 turns those into the
   template's own history. Check its docs step didn't fill in any `{{…}}` placeholder. From 005
   on, `/ship` runs the self-test itself and those prompts go away.

## Direction (not planned; recorded as backlog in the template's own `TODOS.md` by plan 005)

- **Doctrine provenance and an update path.** Plan 005 records `from vibe-starter <version>` in
  each new project's `.bootstrapped`. Next step: a diff-report script that compares a project's
  doctrine files against the template.
- **A scripted "cold-read" check** (the design doc's success criterion #2): a fresh agent recovers
  the testing tiers from the files alone. Run it manually; it's LLM-graded and costs tokens, so
  it shouldn't be a CI gate.

## Findings considered and rejected

Omarchy stack packs (2026-09-25):
- One `omarchy` pack with a sub-option: rejected for three packs named by purpose, which the
  existing mechanism, `--help` and the prompt already handle.
- Pack inheritance (`extends` a full pack): rejected for partial packs (`includes`), which share
  files without coupling one pack's starter to another's.
- A fourth toolkit (GTK4/libadwaita, or C++/Qt 6 as Omarchy's first-party apps use): no gain over
  GPUI for the template, and another language to maintain.
- Walker/Elephant providers and Waybar modules: Omarchy 4 removed both.
- Vendoring Omarchy's plugin validator and scanner: rejected for a sparse clone pinned in
  `.omarchy-ref`, which stays faithful to Omarchy's own code.
- Release automation and AUR packaging: deferred; the generated guides document disktree's
  release layout, which both the AUR and Omarchy's package repository consume.
- Editing a user's Hyprland config from `install.sh`: Omarchy's Lua config has no drop-in
  directory, and Omarchy's own apps print snippets instead.
- A 90% coverage floor on QML: no QML coverage tool exists; the plugin pack holds its JavaScript at
  100% and tests each QML component instead.

JavaScript packs (2026-09-25):
- **Effect v3 (3.22) for the pack.** `@effect/vitest` 0.30 ties it to Vitest 3.2, and so to Vite
  7. Its core runtime costs 35.8 kB gzip, against v4's 7.3 kB. A v3 → v4 migration would follow.
- **React 19.3 + an Effect v4 data layer (Atom) as the first pack.** Prototyped green, at +50.6 kB
  gzip over plain React + Router. Kept as the second pack (backlog), for apps that want React's
  ecosystem.
- **Plain React + TanStack Query + Zod, no Effect.** All stable and the smallest, but it holds
  trust boundaries only by convention. Not planned.
- **Vitest's own thresholds as tier gates.** A glob that matches no file, a Jest-style `global:`
  key and a misspelled metric key all exit 0. A Node tier checker enforces the tiers instead.
- **Other tools.**
  - ESLint + typescript-eslint: it pins TypeScript to 6.
  - Biome: weaker floating-promise detection.
  - `bun test`: no branch coverage.
  - Vite+: a release candidate at planning time.
  - `effect-tsgo patch --oxlint`: it binds Oxlint's version to the patcher's support matrix.
- **A committed `git subtree` of Foldkit's repository** (FOLDKIT.md's suggestion). About 54 MB per
  project, 40 MB of it Foldkit's own copy of Effect, plus Foldkit's maintainer agent files.
  Vendored by script into a gitignored directory instead.
- **`create-foldkit-app` as the pack's scaffolder.** It always runs `npm install` with lifecycle
  scripts, wires the DevTools MCP through unpinned `npx -y`, and turns Oxlint's correctness
  rules off.
- **Routing in the starter.** Its link Commands can't reach 100% in unit tests (`LoadExternal`
  navigates), so routing is left to Foldkit's docs.
- **Turning pnpm's age rule off (`minimumReleaseAge=0`) to resolve the lockfile on release day
  (2026-10-02).** It would let any hours-old transitive dependency into the shipped lockfile.
  Only the train is exempt, and only in the scratch copy that resolves it.

Earlier plans:

- `eval "$(gstack-slug)"` in `bootstrap`: the output is sanitized to `[a-zA-Z0-9._-]` and sets
  only `SLUG`/`BRANCH`. Keeping the guarded call was an explicit design decision (design doc,
  open question 2).
- `npx degit` fallback on a private repo: degit v3 falls back to SSH clone, so it works.
- `README.md` showing raw placeholders on the GitHub landing page: by design (`TEMPLATE.md` is
  the explainer, and the repo is private).
- gitleaks false positives from `node_modules/`: gitleaks' default config already skips it
  (tested).
- 3-part `VERSION` vs gstack's 4-part preference: gstack keeps 3-part versions 3-part
  (`lib/version-source.ts`).
- `## [Unreleased]` in the skeleton changelog vs `/ship`'s "insert after the header" rule:
  counting-house shows `/ship` entries landing correctly below `[Unreleased]`.
- `CHANGELOG.md` in the gitleaks allowlist: deliberate, low risk.
- Porting doctrine drift from the harvest sources: counting-house `TESTING.md`/`ENGINEERING.md`
  changed since the harvest (+25/−4), but the deltas are project-specific.
- Moving *all* skeleton docs into `template/skeleton/`: considered for 005 and deferred. A
  golden inventory of complete placeholder tokens protects them in place; it does not freeze
  arbitrary prose.
- A strict "no `CLAUDE.md` ever" guard and the single-file merge: superseded by the maintainer's
  2026-09-24 choice to retain both files with reciprocal required reading. No shim or
  instruction-file guard belongs in revised 004.
- shellcheck: both scripts are clean today.
- `uv_build` as the Python backend: it can't read a dynamic version, so `VERSION` couldn't be the
  single source. Chose hatchling. (uv, ruff and ty are still the toolchain.)
- The 90% floor in pytest `addopts` (counting-house's style): it trips gstack `/ship` step 7 (G7).
  Moved to `scripts/coverage.sh`.
- Rust `channel = "stable"`: new clippy lints could fail `-D warnings` without a commit. Pinned
  to 1.98.1 instead; revised local verification uses `rustup run` with an already installed
  toolchain, including during bootstrap. Missing prerequisites cannot trigger auto-installation.
- cargo-deny, cargo-nextest, a nightly Rust branch-coverage job, and a Python dependency audit:
  deferred until a project has dependencies (007 maintenance notes).

## Not audited

- The doctrine *content* (`DOCTRINE.md`, `TESTING.md`, `ENGINEERING.md` philosophy). It's the
  maintainer's call; only stale references and gstack conflicts were checked.
- Linux/GNU userland. Every prototype ran on macOS `/bin/bash` 3.2 with bsdtar; plan 001's CI
  covers ubuntu.
- editorconfig-checker was not executed (not installed; the audit was read-only).
- A real `gh repo create --template` round trip (it would create a GitHub repo).
- GitHub Actions itself. No workflow here has run on GitHub. YAML parses and local checks are
  recorded separately; local probes do not establish that the revised workflow has passed.
